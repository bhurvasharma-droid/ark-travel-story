DevOps · Flights Platform CI/CD

The Release Train — 35 pipelines → one gated train.

From a pipeline per service and a human clicking Build, to one gated train — an ephemeral stack brought up, automated regression run against it, then torn down — that records what shipped and explains itself when it breaks.

Before — 35 manual pipelines

A person clicking through each one

  • 35 services, one multi-branch pipeline each, two manual clicks (Build, Deploy) per release.
  • No record of which commit produced which image — nothing could answer “what’s running in prod?”
  • Hotfixes shipped to prod, never merged back, silently lost on the next release.
  • Every red build = 20–40 min of a senior engineer reading logs.
Now — one gated train

Triggered once, records everything

  • One train, 7 stages, triggered once — Jenkins starts it; no one clicks Build or Deploy.
  • Ephemeral env: a real stack is brought up, automated regression (backend + mweb) runs against it, then it’s torn down — cleanup on every path, pass or fail.
  • One record per commit: which gates passed, which image each service got, which commit produced it — queryable, not remembered.
  • On a break, the pipeline explains itself in Slack, log quoted, before anyone asks.

DevOps · when it breaks

A pipeline that explains its own failures.

When a stage fails, only the logs that bear on it are gathered; a model reads them, finds the one thing that broke, and posts a verdict with proof to Slack — every claim quoting the log word for word, or saying it could not tell rather than guessing.
